# 제안서 골격

## 언제 쓰나

디스커버리가 끝나고 제안서를 써야 할 때. "제안서 만들어줘", "제안 목차",
"RFP 답변 구조" 요청.

## 출발점

**제품 소개서가 아니다.** 제안서의 1장은 우리 회사가 아니라 **고객의 문제**로 시작한다.
고객이 자기 문제를 읽고 "우리 얘기를 정확히 이해했구나"라고 느끼지 못하면
뒤의 기능 설명은 읽히지 않는다.

그래서 이 스킬은 디스커버리 기록을 입력으로 요구한다. 없으면 먼저 물어본다 —
내용 없이 목차만 만들면 어느 고객에게나 똑같은, 그래서 아무에게도 안 통하는
문서가 나온다.

## 골격

```
1. 현재 상황 이해
   - 고객이 말한 과제 (고객 표현 그대로, 출처 명시)
   - 그 과제가 만드는 비용 (수치가 있으면 수치로)
   - 지금 방식의 한계

2. 목표 상태
   - 도입 후 무엇이 달라지는가 — 고객의 지표로 서술
   - 성공 기준 (측정 가능한 형태)

3. 해법
   - 과제 → 해당 기능 매핑 (1장의 항목과 1:1로 대응할 것)
   - 우리만 되는 부분이 있으면 여기, 없으면 억지로 만들지 않는다

4. 도입 계획
   - 단계, 기간, 각 단계의 산출물
   - 고객이 투입해야 하는 리소스 — 숨기지 않는다

5. 투자
   - 비용 구조
   - 1장의 비용과 비교 (ROI를 주장하려면 여기서)

6. 다음 단계
   - 이 문서를 읽은 사람이 할 수 있는 구체적 행동 하나
```

## 규칙

**1장과 3장은 항목 수가 같아야 한다.** 고객이 말하지 않은 과제를 3장에서 풀면
안 되고, 고객이 말한 과제를 3장에서 빠뜨려도 안 된다. 이 대응 관계가 제안서의 뼈대다.

**근거 없는 절은 비워 둔다.** `[디스커버리에서 미확인 — 확인 필요]`라고 적는다.
채워 넣은 추측은 고객 앞에서 틀렸을 때 신뢰를 통째로 깎는다.

**ROI 계산은 고객이 준 숫자로만 한다.** 업계 평균이나 우리 벤치마크를 고객 수치인 척
쓰지 않는다. 출처를 밝히면 참고 자료로는 쓸 수 있다.

**분량 목표를 먼저 정한다.** 실무 검토용은 5~8장, 임원 보고용은 3장 이내 요약이
앞에 붙는다. 목적을 모르면 물어본다.

## 하지 말 것

- 경쟁사를 이름으로 깎아내리는 절 — 제안서에 남으면 불리하게 돌아온다.
- 고객사 담당자의 개인정보를 표지나 이력에 넣는 것 — [[customer-data-handling]] 참고.
- 확정되지 않은 가격을 확정처럼 쓰는 것. 유효기간과 전제를 반드시 붙인다.
